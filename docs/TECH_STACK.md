# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core, with each query written once for both databases: Supabase's Postgres when `DATABASE_URL` is set, through psycopg in the `undercover` schema (set with `search_path` on each connection) with a pool of at most 4 connections, and SQLite otherwise, as in the tests. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount; the payout rules are an operation too. The backend calls the agent's service only through `backend/agent_client.py`, and never imports the agent.
- `agent/`: two agents on OpenRouter. The queue agent, `run_queue(cap)`, is built with LangChain's `create_agent` and runs the queue, handing each claim to the claim agent. The claim agent is a hand-written LangGraph graph (`StateGraph`, with agent, tools, outcome, sign-off and pay nodes) that works one claim on its own thread, saves its progress after every step with LangGraph's Postgres checkpointer (`PostgresSaver` on a psycopg pool of at most 4 connections in the `undercover` schema, or in memory in the tests) with `durability="sync"`, waits for a handler's sign-off with `interrupt()` and resumes with `Command(resume=...)`. The agent stays synchronous, since async Postgres connections don't work with Windows' default event loop. The code is in five parts: `api.py`, the only client of the backend; `harness.py`, everything around the model that knows nothing about claims: the model, the Langfuse tracing, the checkpointer, the retry policies (LangGraph's `RetryPolicy`), steps from replies and results, the one refusal message, and the queue agent's middleware (LangChain's `ModelRetryMiddleware`, `ToolRetryMiddleware` and `ModelCallLimitMiddleware`, with our own refusals and check before finishing); `tools.py`, every tool, with the queue agent's state in LangChain's runtime context (`context_schema` and `ToolRuntime`); `agents.py`, which builds and runs the two agents, with the claim graph's model in LangGraph's runtime context; and `service.py`, the agent's FastAPI service and its entry point beside the backend. Both agents reach claims, documents and instructions only through the backend's API. They use `deepseek/deepseek-v4.1-flash` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`. Each claim's thread is traced in Langfuse in one session named after the thread, such as `CLM-1008-3f9a2c1d`.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Langfuse keys (`LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL`) and Supabase's session pooler connection string (`DATABASE_URL`). `npm run dev` passes it to the backend and the agent's service, `uv run -m agent` loads it itself, and the tests never read it. The agent's service is at `UNDERCOVER_AGENT`, or `http://127.0.0.1:8002` by default.
