## What's built

- `backend/`: FastAPI on SQLAlchemy Core. With `DATABASE_URL` set, as `npm run dev` does from `.env`, the records are on Supabase in the `undercover` schema, with at most 4 connections; otherwise on SQLite at `DATABASE_PATH` or `backend/undercover.db`, as in the tests. The database is created from `data/` on first use and never reads `data/evals/`. It serves the claims queue, each claim with its thread, policies, customers, a customer's claim history, the handlers, the policy wording and the claims manual (in full, or by numbered section), the agent's instructions (`backend/instructions/`), runs of the agent with their to-do lists, and the payout rules from the Week 2 Day 1 lab (`backend/payout.py`, `POST /api/policies/{policy_id}/payout`), with the approval limit from `data/company.json`.
  - A claim moves from `waiting` to `in_progress` when it starts, on a new thread such as `CLM-1008-3f9a2c1d`. A decline or a referral is `decided`. An approval stays `in_progress` until it's paid, or goes to `awaiting_sign_off` over $1,000.00; a sign-off records the handler and the time and puts the claim back `in_progress`, and the payment, which copies the sign-off, makes it `decided`. A release counts a failure on an undecided claim in progress: the first returns it to `waiting`, the second leaves it `left_for_handler`.
  - Nothing happens twice: a repeat of the recorded decision or payment returns the claim, and a different one is refused. A payment over the limit is refused until a handler signs off.
  - After a sign-off is saved, the backend asks the agent's service to carry the claim on, without waiting; if the service can't be reached the sign-off stands. "Run the agent" asks the service to work a claim, and says so if it isn't running. Every call to the service is in `backend/agent_client.py`, at `UNDERCOVER_AGENT` or `http://127.0.0.1:8002`.
- `agent/`: the UnderCover Agent on `deepseek/deepseek-v4.1-flash` with low reasoning effort, or `MODEL_NAME`, in five modules that import one way, `service`/`__main__` → `agents` → `tools` → `api`, with `harness` beside them:
  - `api.py`: every call to the backend, with its base URL. A refusal raises `Refused` with the backend's reason. A test checks that no other module in `agent/` names an API path.
  - `harness.py`: everything around the model, knowing nothing about claims: the model; the Langfuse tracing, one session per thread, on when the Langfuse keys are set; the checkpointer, `PostgresSaver` on a pool of at most 4 connections in the `undercover` schema with `DATABASE_URL`, in memory otherwise; LangGraph retry policies for model calls (three retries) and for tool calls that can't reach the backend (two); turning replies and tool results into steps; the one refusal message; and the queue agent's middleware.
  - `tools.py`: every tool. The claim agent's seven: `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `read_section`, `calculate_payout`, which uses the backend's payout rules, and `record_decision`. The queue agent's three: `list_waiting_claims`, `write_todos` and `work_claim`, which hands one claim to the claim agent and returns a one-line report, such as "CLM-1001: approved, $420.00, paid.".
  - `agents.py`: the claim graph, `START → agent ⇄ tools → outcome → sign_off → pay`, with its model in LangGraph's runtime context. `agent` calls the model and stops the claim at 30 model calls, counted in the graph's state across restarts; `tools` runs the tools with `ToolNode`, passing a refusal back to the model; both record every step on the claim. `outcome` reads the claim from the backend; `sign_off` waits with `interrupt()` when the backend says the claim is `awaiting_sign_off`; `pay` pays an approval. Every run is invoked with `durability="sync"`. `work_claim(claim_id)` starts a claim on a new thread; `carry_on(claim_id)` resumes a thread with the handler's sign-off, or from its last step after a stop. A claim that fails with an error is released and starts afresh on a new thread; Ctrl-C or a kill leaves it in progress to carry on. `run_queue(cap)` first carries on every claim in progress, then finishes a run left running, then runs the queue agent as before.
  - `service.py`: the agent's service on port 8002, with `work_claim` and `carry_on_claim`, each replying `202` and working in the background.
- `dashboard/`: the claims desk in the UnderCover brand, light and dark. `api.ts` holds every endpoint with its type.
  - The queue (`#/`), with counts in each of the five states and the agent's latest run above the table.
  - Each claim (`#/claims/CLM-1001`): the story, items, documents, policy and customer, the agent's decision and payment, what the agent read, and its steps as they happen. "Run the agent" on a waiting claim, and "Sign off" on a claim waiting for sign-off. A signed-off claim says who signed it off and that the agent is paying it; a paid claim says who signed it off and when.
  - The agent's instructions, read only (`#/instructions`).
- `e2e/`: Playwright tests on their own servers (ports 8001 and 5174) and SQLite database, with `e2e/agent-stand-in.ts`, a stand-in for the agent's service on port 8003 that records each call and pays a signed-off claim through the backend.

## Running it

- `npm run dev` starts the backend on port 8000, the agent's service on port 8002 and the dashboard at http://localhost:5173, with `.env`, so on Supabase.
- `npm run seed` resets Supabase to the data in `data/`: it drops and recreates the `undercover` schema, checkpoints included. Restart `npm run dev` afterwards. `uv run -m backend.seed` resets the local SQLite database.
- "Run the agent" on a claim, or `uv run -m agent CLM-1001`, runs the agent on one claim. Each run calls the model, a few cents with the default model.
- `uv run -m agent --cap 5` first carries on any claim in progress, then runs the queue agent on at most five claims. It prints each claim's report as it comes, then the summary.
- Signing off a claim on the dashboard has the agent's service pay it within a few seconds. If the service isn't running, the next `uv run -m agent` pays it.
- `npm run check` runs every check, with no `.env` needed.
