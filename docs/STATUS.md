## What's built

- `backend/`: FastAPI on SQLAlchemy Core. With `DATABASE_URL` set, as `npm run dev` does from `.env`, the records are on Supabase in the `undercover` schema, with at most 4 connections, and a request waits up to 120 seconds for one; otherwise on SQLite at `DATABASE_PATH` or `backend/undercover.db`, as in the tests. The database is created from `data/` on first use. It serves the claims queue, each claim with its thread, policies, customers, a customer's claim history, the handlers, the policy wording and the claims manual (in full, or by numbered section), the claim agent's instructions (`backend/instructions/claim.md`), the runs, and the payout rules from the Week 2 Day 1 lab (`backend/payout.py`, `POST /api/policies/{policy_id}/payout`), with the approval limit from `data/company.json`.
  - A claim moves from `waiting` to `in_progress` when it starts, on a new thread such as `CLM-1008-3f9a2c1d`. A decline or a referral is `decided`. An approval stays `in_progress` until it's paid, or goes to `awaiting_sign_off` over $1,000.00; a sign-off records the handler and the time and puts the claim back `in_progress`, and the payment, which copies the sign-off, makes it `decided`. A release counts a failure on an undecided claim in progress: the first returns it to `waiting`, the second leaves it `left_for_handler`.
  - Nothing happens twice: a repeat of the recorded decision or payment returns the claim, and a different one is refused. A payment over the limit is refused until a handler signs off.
  - `records.py` is the one way to look up a record. `runs.py` creates a dispatch, choosing every claim in progress and every waiting claim, oldest submitted first, and loads a run with each claim's cost and time, its totals and its summary, which it builds when read, in a fixed number of queries. `model_calls` and `work_times` hold each call and each stretch of work with its run, or with none.
  - `evaluations.py` makes an evaluation's copies, each with a new id in its row and its record, and scores them. `scoring.py` has the measures as pure functions. The answer key is in `handler_decisions` and `held_out_claims`, seeded from the three named files in `data/evals/`. `get_claim` on a copy has the same fields as on any claim, so the agent can't tell the difference; `get_claim_evaluation` tells the dashboard. A copy can't be run or signed off.
  - After a sign-off is saved, the backend asks the agent's service to carry the claim on, without waiting; if the service can't be reached the sign-off stands. Starting a dispatch, an evaluation or "Run the agent" goes through the service, passing on its refusal as a 409 and saying so with a 503 if it isn't running. Every call to the service is in `backend/agent_client.py`, at `UNDERCOVER_AGENT` or `http://127.0.0.1:8002`.
- `agent/`: the UnderCover Agent on `openai/gpt-6-luna` with low reasoning effort, or `MODEL_NAME` with none, in six modules that import one way, `service` → `dispatcher` → `agents` → `tools` → `api`, with `harness` beside them:
  - `api.py`: every call to the backend, with its base URL. A refusal raises `Refused` with the backend's reason. A test checks that no other module in `agent/` names an API path.
  - `harness.py`: everything around the model, knowing nothing about claims: the model and each reply's usage; the Langfuse tracing, one session per thread with an optional tag, on when the Langfuse keys are set; the checkpointer, a `PostgresSaver` of its own for each claim run on one shared pool of at most 4 connections in the `undercover` schema with `DATABASE_URL`, in memory otherwise; LangGraph retry policies for model calls (three retries), for tool calls that can't reach the backend (two) and for a whole stretch of work (waits of 5, 10 and 20 seconds with jitter); turning replies and tool results into steps; and the one refusal message.
  - `tools.py`: the claim agent's seven tools: `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `read_section`, `calculate_payout`, which uses the backend's payout rules, and `record_decision`.
  - `agents.py`: the claim graph, `START → agent ⇄ tools → outcome → sign_off → pay`, with its model and the run's id in LangGraph's runtime context, so that a claim carried on in a later run charges that run. `agent` calls the model, records the call and stops the claim at 30 model calls, counted in the graph's state across restarts; `tools` runs the tools with `ToolNode`, passing a refusal back to the model; both record every step on the claim. `outcome` reads the claim from the backend; `sign_off` waits with `interrupt()` when the backend says the claim is `awaiting_sign_off`; `pay` pays an approval. Every run is invoked with `durability="sync"`, and each stretch of work is recorded, so a wait for a sign-off is never counted. `work_claim(claim_id)` starts a claim on a new thread; `carry_on(claim_id)` resumes a thread; both do nothing if this process is already working the claim. A rate limit or a timeout goes through as it is, for a retry to carry on. Any other error, or an end with no decision, releases the claim. `work(claim_id, run)` is the only way in for the dispatcher, and clears a copy's thread when it finishes.
  - `dispatcher.py`: the graph with no model, `list_claims` → one `Send` per claim → `work_claim`, with `max_concurrency` set to N, the `RetryPolicy` and an `error_handler`. `dispatch(n)` and `evaluate(n, claim_set, tiny)` create the run through the backend, work it and finish it; a run that fails outright is `stopped`.
  - `service.py`: the agent's service on port 8002, with `work_claim`, `carry_on_claim`, `start_dispatch` and `start_evaluation`, each replying `202`. A dispatch or evaluation works in a daemon thread and takes the one run slot, so a second start gets a `409`. When the service starts, it waits up to a minute for the backend and marks any run still running as `stopped`.
- `dashboard/`: the claims desk in the UnderCover brand, light and dark. `api.ts` holds every endpoint with its type.
  - The queue (`#/`), with counts in each of the five states. The run panel chooses N and starts a dispatch, and shows the latest one's state, model cost and time, each claim with its cost and time, and its summary when it ends.
  - Each claim (`#/claims/CLM-1001`): the story, items, documents, policy and customer, the agent's decision and payment, what the agent read, and its steps as they happen. "Run the agent" on a waiting claim, and "Sign off" on a claim waiting for sign-off. A signed-off claim says who signed it off and that the agent is paying it; a paid claim says who signed it off and when. An evaluation's copy says so, links back, and has neither form.
  - The Scoreboard (`#/scoreboard`): a form for N, the set and whole or tiny, then the evaluations, newest first, with every measure. Each opens (`#/scoreboard/evaluation-3f9a2c1d`) to its settings, its measures and its claims, with the handler's decision and payout beside the agent's and a "Miss" chip on each miss.
  - The claim agent's instructions, read only (`#/instructions`).
- `e2e/`: Playwright tests on their own servers (ports 8001 and 5174) and SQLite database, with `e2e/agent-stand-in.ts`, a stand-in for the agent's service on port 8003 that records each call with what it was given and pays a signed-off claim through the backend.

## Running it

- `npm run dev` starts the backend on port 8000, the agent's service on port 8002 and the dashboard at http://localhost:5173, with `.env`, so on Supabase.
- `npm run seed` resets Supabase to the data in `data/`: it drops and recreates the `undercover` schema, checkpoints and the scoreboard included. Restart `npm run dev` afterwards. `uv run -m backend.seed` resets the local SQLite database.
- "Start a dispatch" on the queue page works the queue, and "Start an evaluation" on the Scoreboard page works copies of a set. On the default model a claim costs about $0.0013, so a whole queue costs about three cents.
- "Run the agent" on a claim, or `uv run -m agent CLM-1001`, runs the agent on one claim. Don't run the command beside a dispatch: the set of claims being worked belongs to one process, and only the service's dispatches and sign-offs share it.
- Signing off a claim on the dashboard has the agent's service pay it within a second or so. If the service isn't running, the next dispatch pays it.
- `npm run check` runs every check, with no `.env` needed.
